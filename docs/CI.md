# This repo's CI workflow

Extracted verbatim from CLAUDE.md (1.85x over its 40,000-character budget). THREE
near-duplicate `.github/workflows/ci.yml` bullets had accumulated there; all three are
kept below in file order rather than merged, for the same reason as docs/CMD.md.

- `.github/workflows/ci.yml` — CI workflow: `host-build` (from source, host-native binary — its cache-validation step execs `build/go-toolchain`, which is safe only because that job never builds the APE), `build` (the composite action with `targets: cosmo,darwin/amd64,darwin/arm64,windows/arm64` — the APE plus the three native carve-outs, autorelease off; the cosmo bootstrap downloads the gosmopolitan toolchain from its default `?branch=master`), three `smoke-*` jobs (each `timeout-minutes`-bounded) that download the `go-build-build` hand-off the `build` job uploaded via `wow-look-at-my/actions@cache-download#latest` (run-keyed cross-OS cache wrapper; the download `path` is the destination directory; the action names its hand-off `go-build-<job id>` per calling job, so concurrent same-run jobs never collide on one key) and EXECUTE throwaway copies of the artifacts in `dist/` on linux/macOS/Windows runners — linux: APE magic `MZqFpD` on the linux/amd64 slot + `version` + `--help` + the FULL default pipeline in a tiny module under the APE, plus a agent-output-guard assertion on a fresh throwaway APE copy (per-command `CLAUDECODE=1` — never job-wide, the other smoke steps must stay inert — with stdout to /dev/null must exit 1 with the "refused to run" message, and `version` must stay exempt); macOS: asserts the darwin/arm64 slot is native Mach-O (`cffaedfe`) and runs the FULL pipeline with that native binary (the consumer-critical mac gate), plus a REDUCED APE gate (magic on a linux slot + `version` + `--help` inside a module = official-Go bootstrap under the APE loader) because the pipeline WEDGES AT EXIT under the APE on macOS — root-caused (SIGQUIT dumps, run 28742069477; issue #276) to the fork running unix-socket fds blocking/netpoller-less on darwin hosts so the cache daemon's Listener.Close deadlocks; all pipeline PHASES are green under the APE now that cacheProgCommand wraps the GOCACHEPROG self-exec in a sh script; Windows runs `version`/`--help` only (gobootstrap's .tar.gz URL has no windows variant on go.dev; owner-ruled smoke contract: NO workflow-side Go provisioning — no `setup-go`, that bypasses the bootstrap requirement — `--help`'s bootstrap must resolve the runner image's EXISTING Go via the APE's OWN NT-side `exec.LookPath`, so no help-flag `needsGo` carve-outs either; broken pre-gosmopolitan#63, fixed in fork v237+; if the image ever drops Go, the red is honest — escalate to the owner) — and `publish` (the single publish path, gated on all three smokes: the same `go-build-build` hand-off downloaded into `build/`, then `wow-look-at-my/buildhost`'s buildhost-publish action publishes it via its `path` input and OIDC — no checkout, no artifacts API; the job's `deployments: write` + `artifact-metadata: write` are what let the action register the Deployment and post the storage record (mandatory, no opt-out) — with a trailing `if: always()` `wow-look-at-my/actions@cache-cleanup#latest` step, backed by the job's `actions: write`, that deletes the run's `cache-xfer-*` hand-off entries and age-sweeps 12h-old leftovers). CI uses NO GitHub Actions artifacts: job hand-offs ride the `wow-look-at-my/actions@cache-upload#latest`/`@cache-download#latest` actions (run-keyed GitHub cache entries — exact key includes run_attempt, downloads fall back to the run's previous attempt, absence fails loud; a single-file upload like the `host-build`→`build` `host-go-toolchain` hand-off of `build/go-toolchain` is stored raw and restored basename+exec-bit into the destination directory, where the action's `binary` input consumes it), and the old debug-only `build-profiles` artifact is dropped (the profile's home is the Step Summary table). The tidy phase self-heals against cache-served module-index damage: `src/cmd/modindexretry.go`'s `runModTidy` detects cmd/go's `corrupt index` failure (a damaged or mis-keyed module-index cache entry passes every content gate the cacheprog can apply — no build id, opaque action key), disables the Go module index for the remainder of the run (`GODEBUG=goindex=0`), and retries once
